### 概要
 - ハッカソン形式
 - チームは7人（バックエンド4人、フロントエンド3人）
 - フロントエンドのリーダーとして、作業の割り振りとプルリクエスト（PR）のレビュー、一部のページとフロントエンドの API 部分の実装を担当した

### 困難と対応
 - 話し合いでは、発言が特定のメンバーに偏っていた。そこで、全員に順番に意見を言ってもらう、発言の少ないメンバーに「〇〇さんはどう思う？」と直接聞く、といった形で全員の意見が出るようにした。

 - 開発中、フロントエンドとバックエンドがそれぞれ新しい機能に合わせて API の形式を独自に変えてしまい、互いの形式が合わなくなった。片方の作業が遅れていても、もう片方がそれに気づけないこともあった。これには二つの対策をとった。一つは、別のメンバーが始めた1時間ごとの進捗報告会である。全員が集まって変更と進み具合を共有した。もう一つは、現在の API 形式をまとめたドキュメントである。これは自分が担当し、フロントエンドとバックエンドの両方のリポジトリに置いた。実装を AI コーディングエージェントに任せるときもこのドキュメントを読ませたので、人が書く部分もエージェントが書く部分も同じ形式に揃った。

### うまくいったこと
 - 分担は、いきなり割り振るのではなく、まず全員で必要なタスクを洗い出してから決めた。序盤は、ほかの部分から強く依存される箇所と、どこにも依存せずに作れる箇所を別々のメンバーに割り当てた。依存される箇所を先に進めている間も、ほかのメンバーは単独で作れる箇所に取りかかれるので、手が空く人が出にくい。担当のない待ち時間は、環境構築中の45分 × 2人分に抑えられた。

 - フロントエンドの PR は基本的に自分がレビューした。当初はすべての観点を自分が確認していたが、フロントエンドの進みがバックエンドより遅れていたため、途中から自分はコードの品質だけを確認してマージし、UI / UX の確認はマージ後に手の空いていたバックエンドのメンバーに任せた。これにより、PR のレビュー待ちの時間は平均45分から15分に短くなった。
