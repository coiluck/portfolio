### 概要
 - 3日間のハッカソン形式。与えられた課題に対して、4人チームで Web アプリケーションを開発した
 - フレームワークは使わず、HTML と JavaScript だけで実装した
 - リーダーではなく、チームの一員として参加した

### 困難と対応
 - メンバー間で開発経験に差があり、自分が書いた中核処理をほかのメンバーがうまく使えなかった。まず関数の引数と戻り値の意味を説明した。それでも難しかったため作業範囲を入れ替えてデータを受け取るまでを自分が書き、受け取った後の処理だけを担当してもらう形に分担を変えた。
 - プログラミング未経験のメンバーがいたため、自分の担当と並行してそのメンバーのサポートを引き受けた。CSS を担当してもらい、最初は「背景の色を変える」のように内容がはっきりした小さなタスクを渡した。最後には「この要素に足りないところを自分で考えてスタイルを当てる」というタスクを渡し、自分で判断する範囲を段階的に広げた。
 - アプリに AI を組み込みたいという意見が根強かった。開発初期の技術選定で意見を伝えきれなかった反省（反省点を参照）から、この議論では自分から提案し、「AI を使うこと自体が目的にならないよう、先に解決したい課題と実装する機能を決め、その処理に AI が最適な場合だけ使う」という順番で進めることにした。この順番で機能を決めた結果 AI が最適な処理はなかったため、使わなかった。

### 反省点
 - 技術選定で自分の意見を伝えきれなかった。ほかのメンバー全員がフレームワークの経験がないことを理由に、フレームワークを使わない案にすぐ決まった。メンバーの経験に合わせる判断には妥当な面もあるが、3日間で作る規模や、フレームワークを使う利点と学習コストを比べる議論はしていない。結論が同じになったとしても、判断の基準を示して全員で比較する場をつくるべきだった。
 - 作業範囲と変更の共有方法を決めていなかった。メンバーの Git の学習コストを考えて zip ファイルでコードを共有していたが、この方法では変更履歴を追いにくい。そのため、意図が共有されないまま自分が書いた処理が書き換えられていても、しばらく気づけなかった。Git を使わないのであれば、ファイル単位で担当を分けるなど、作業範囲を最初に決めておくべきだった。

### 学んだこと
 - リーダーという立場でなくても、チームの方針が決まる場面では、積極的に提案する必要がある。
 - 作業範囲や変更の共有方法は、明示的に決めないと各自の判断では揃わない。特に開発経験に差があるチームでは、開発の最初に決めておく必要がある。
