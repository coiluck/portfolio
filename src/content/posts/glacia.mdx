## 作品概要

キャラを編成し、HEX マスの盤面で移動・攻撃して戦うシミュレーション RPG。戦闘で手に入る素材でキャラを育てる。ブラウザで動き、第1章（6ステージ）まで遊べる。アカウントを作ると、どの端末からでも同じデータで続きを遊べる。

| 項目 | 内容 |
| --- | --- |
| 開発体制 | 1人（企画・プログラム〔画面／サーバー〕・UI・データ設計） |
| 動作環境 | ブラウザ（Chromium 系推奨） |
| 画面側 | TypeScript／React 19／zustand／Vite |
| サーバー側 | Cloudflare Workers／Cloudflare D1（SQLite） |

## 作った理由

### 課題
これまでの自作ゲームは友人の端末では意図と違う大きさで表示されたり、セーブデータが消えたりして、遊んでもらうまでに問題があった。

配布とデータの保存の方法は、作品ごとに変えてきた。

  </FlowItem>
  <FlowItem title="Electron／Tauri">

  </FlowItem>

本作の目標はどの端末でも同じ見た目、同じデータで続きを遊べることにした。見た目は画面の拡大縮小で、データはサーバーで揃える。

## 端末によって見た目が変わる問題

これまでの作品ではメディアクエリで画面幅ごとにレイアウトを切り替えていた。この方法では切り替えの境目ごとに別のレイアウトになるので、自分の開発環境で確認した見た目と友人の PC で表示される見た目が一致しなかった。

アルバイト先で入力内容のプレビューを画面に収まる大きさで表示する機能を作っていた。このとき使った「全体を拡大縮小して画面に収める」方法がゲームの表示にもそのまま使えると気づいた。

画面は2つの層に分けている。

| 層 | 大きさ | 置くもの |
| --- | --- | --- |
| セーフエリア | 1920 × 1080を比率を保って拡大縮小 | 盤面・メニューなど、見切れると困る中央に配置するもの |
| ビューポート | 端末の画面全体 | 背景、画面の端に寄せるボタン |

![スクリーン設計図](/images/posts/glacia/screen.avif)

拡大率は `min(画面の幅 / 1920, 画面の高さ / 1080)` で求めて CSS 変数 `--scale` に書き込み、ウィンドウの大きさが変わるたびに計算し直す。縦横の短いほうに合わせるので、セーフエリアはどの端末でも全体が画面に収まる。

16 : 9 でない画面ではセーフエリアの外に余白ができる。そこで背景はビューポート全体に敷き、端に寄せるボタンはセーフエリアではなく画面の端からの距離で置いた。これで画面の比率が変わっても余白が目立たない。

## ゲーム内の値をサーバーで決める設計

ガチャ、戦闘の報酬、キャラの強化など、ゲーム内の値が変わる操作はすべてサーバーで計算する。ブラウザ側の状態は開発者ツールで書き換えられるので、画面側で計算した値を保存すると所持数などをいくらでも増やせてしまうからだ。画面側の状態（zustand）は表示にだけ使う。

サーバーには Cloudflare Workers を選んだ。無料枠が大きいこと、データベース（D1）を同じサービスの中で使えること、画面側と同じ TypeScript で書けることが理由である。最後の点は、後で書くように計算の関数を画面側と共有するうえで必要だった。

### 1回の操作の流れ

10連ガチャを例にすると、1回の操作は次のように処理する。

<Mermaid code={`
sequenceDiagram
  actor P as プレイヤー
  participant B as 画面<br>React＋zustand
  participant W as Cloudflare Workers
  participant D as D1
  P->>B: 10回引く
  B->>W: POST /gacha/pull { count: 10 }＋トークン
  W->>D: トークンからユーザーを特定
  W->>D: ユーザーデータを読む
  W->>W: 抽選・ジェムの消費を計算
  W->>D: 変わった行だけ書き込む
  W-->>B: ユーザーデータ全体＋抽選結果
  B->>B: 全ストアを置き換える
  B-->>P: 演出と結果を表示
`} />

どの操作も「読む → 計算する → 保存する → 返す」の順になるので、この部分は Workers 側で1か所にまとめた。操作ごとに書くのは、操作前のユーザーデータとリクエストの中身を受け取って、操作後のユーザーデータを返す関数だけである。

```ts
// 操作ごとの関数の型
type Command<T> = (me: MeResponse, body: unknown, ctx: Context) => { me: MeResponse; result: T }

// すべての操作で共通の処理
const before = await loadMe(ctx)                         // D1 から読む
const after = command(before, await request.json(), ctx) // 計算する
await saveMe(ctx, before, after.me)                      // 変わった行だけ書く
return json({ me: after.me, result: after.result })
```

誰の操作かは、リクエストの中身ではなくログイン時に発行したトークンから決める。パスワードはソルトとペッパーをつけてハッシュ化し、トークンも D1 にはハッシュで保存している。ログインに失敗したときは、ユーザー名とパスワードのどちらが違ったかを返さない。

### 途中からサーバーへ移行した

サーバーは最初からあったわけではない。最初の約2か月半は、画面側のストアを直接書き換えてゲームを作っていた。2026/09 に、値を変える処理をサーバーへ移した。移行は2段階で行った。

<Flow numbered>
  <FlowItem title="計算をストアから切り出す">
    値を変える処理を、ストアの中から `features/` の関数に移した。関数は「操作前のデータ → 操作後のデータ」の形にし、まずはモックから呼んだ
  </FlowItem>
  <FlowItem title="Workers に差し替える">
    Workers と D1 を用意し、同じ関数を Workers から呼ぶようにした。画面側の変更はモックを消すことがほとんどだった
  </FlowItem>
</Flow>

計算の関数は画面にもサーバーにも依存しないように書いたので、Workers 側は画面側のソースコードから直接 import している。同じ計算を画面側とサーバー側の2か所に書かずに済む。

### 毎回ユーザーデータ全体を返す

どの操作でもユーザーデータ全体を返し、画面側はそれで全ストアを置き換える。操作ごとに「何が変わったか」を返して反映する処理を書かずに済み、画面とサーバーの値がずれても次の操作で揃う。

そのため操作のたびにユーザーデータをすべて読むことになる。D1 の無料枠は読み取りが1日500万行までなのでアイテムやミッションの進行などは正規化せず、`users` テーブルの1行に JSON の列として持たせて、読む行数を減らした。

### 通信と書き込みを減らす

無料枠を使い切らないように操作が多い箇所は通信をまとめた。無料プランでは1日の上限を超えるとリセットされる日本時間の朝9時まで D1 にクエリを送れなくなり、ゲームが遊べなくなる。

例えば編成やお知らせは画面を出るときに1回だけ保存しているし、戦闘中の盤面はサーバーに送らず結果だけを送る。戦闘中の仕様はユーザーが不正な API を送って本来ユーザーがクリアできないステージをクリアできたと偽ることができるという欠点があるが、

1. 同じ画面で何度も試行錯誤（戻るボタンがあるので）すると書き込みも多くなる
2. これは一人向けゲームである

という理由から不正なクリアには目をつむることに決めた。これについては[後述する対策](#残っている課題)を取れば解決できるはずだ。

サーバー側でもユーザーデータのうち操作の前後で変わった行だけを書き込む。

## 戦闘の仕組み

<Figure src="/images/posts/glacia/battle.avif" alt="戦闘画面">戦闘画面（赤い範囲はスキルの効果範囲のプレビュー）</Figure>

### HEX 座標

HEX マスの座標の持ち方は1通りではない。[Red Blob Games の解説](https://www.redblobgames.com/grids/hexagons/)で主な座標系を比べ、斜交座標を選んだ。

| 座標系 | 持ち方 | 隣接マス | 距離・回転 |
| --- | --- | --- | --- |
| オフセット座標 | 行と列（2次元配列と同じ） | 偶数行と奇数行で差分が変わる | 一度ほかの座標系への変換が要る |
| キューブ座標 | (q, r, s)、ただし q + r + s = 0 | 6方向の差分を足すだけ | 式1つで求まる |
| 斜交座標 | キューブ座標から s を省いた (q, r) | 同上 | 同上（s = −q − r で戻せる） |

オフセット座標は見た目どおりで分かりやすいが、行の偶奇で計算が分かれ、移動範囲やスキル範囲の計算が複雑になるため不採用。キューブ座標は計算が単純だが、値を1つ余分に持つ。斜交座標はキューブ座標と同じ計算をそのまま使え、値は2つで済む。

### スキルの範囲をデータで書く

スキルは、狙えるマス（射程）と、そこに当たったときに効果が及ぶマス（効果範囲）をデータで定義する。範囲の判定は共通の処理で行うので、スキルを増やしても判定側のコードは変えない。

範囲の形は2種類ある。

| 種類 | 定義 | 向き |
| --- | --- | --- |
| 距離型（`range`） | 自分からの距離が min 以上 max 以下のマス | なし |
| 形型（`pattern`） | 東向きを基準にした相対座標の集まり | 6方向のどれかに回して使う |

たとえば以下のスキルは隣の1マスを狙い、狙ったマスと術者から見たその左右の計3マスに当たる（以下は定義の一部）。

```ts
{
  id: 'hoge',
  apCost: 4,
  range: { kind: 'range', max: 1 },  // 射程: 隣の1マス
  effect: [{
    type: 'damage', power: 160, target: 'enemy',
    // 効果範囲: 狙ったマスと、術者から見たその左右
    area: { kind: 'pattern', offsets: [{ q: 0, r: 0 }, { q: 0, r: -1 }, { q: -1, r: 1 }] },
  }],
}
```
最初は距離だけで決まる range 型（自分から min 以上 max 以下の距離の1マスを選ぶスキル）のスキルしかなかったため回転が不要で、座標は斜交座標だけで扱えると考えていた。その後に形型を追加すると形を6方向に回す処理が必要になった。回転はキューブ座標のほうが式が単純なので、この処理の中だけ斜交座標からキューブ座標に戻して回している。

範囲をデータで書くようにしたことで、不具合をデータの修正で直せたこともある。以前は「自分のマスは射程の形に関係なく常に狙える」という例外を判定処理に入れていた。これは「`target` が `enemy` なら自分は選んでもダメージを受けないし、`target` が `ally` のスキルは回復とかなので自分も狙えたほうがいい」という理由での実装だったが、この例外のせいで、射程に自分のマスを含まないスキルでも自分のマスを狙えてしまい、効果範囲が複数マスに及ぶスキルでは射程では狙えない隣の敵にまで当たっていた。。例外を消し、自分を対象にするスキルは射程を `{ kind: 'range', min: 0, max: 0 }` と明示的に書くようにして直した。

## コード構成

```text
src/
  api/          サーバーとの通信
  data/         キャラ・ステージ・敵・ドロップ等の定義
  features/     ゲームのルール（画面に依存しない）
    battle/       戦闘・HEX・敵の行動
    characters/   育成
    gacha/ mission/ stamina/ ...
  layouts/      画面の拡大縮小
  pages/        画面ごとのコンポーネント
  stores/       状態管理（zustand）
worker/
  src/routes/   API の各操作
  schema.sql    DB 定義
```

- ゲームのルールは `features/` に関数として分け、画面（`pages/`）からは呼び出すだけにした。サーバー（`worker/`）も同じ関数を使う
- キャラ・スキル・ステージ・敵・ドロップ・ミッションはデータとして定義し、追加のときにルール側のコードは触らない
- キャラの基本性能（マスター）とプレイヤーごとの所持状態やレベル（ユーザー）を分けて持ち、表示のときに合成する。D1 に保存するのはユーザーのほうだけである

## 残っている課題

戦闘の勝敗は画面側から「勝った」「負けた」を送っている。戦闘は画面側で進めるので、サーバーは勝敗の申告をそのまま受け取るしかなく、実際には勝っていない戦闘の報酬を受け取るリクエストも送れてしまう。報酬の中身とドロップの抽選はサーバーで決めているが、勝敗そのものは検証していない。

対策としては戦闘中の操作の記録を結果と一緒に送り、サーバーで同じ戦闘を再現して勝敗を確かめる方法が考えられる。戦闘の処理は `features/battle/` の関数にまとまっていて乱数も使っていないので、同じ操作の列を与えればサーバーでも同じ結果が得られる。

ただこのゲームには他のプレイヤーと関わる要素がなく、不正をしても影響はそのプレイヤー自身のデータにしか及ばない。まだ開発中でほかに作るべき機能が多いので、この対策は優先度を下げて未実装にしている。
