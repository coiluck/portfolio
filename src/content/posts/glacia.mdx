## 作品概要

- **何を作ったか**：キャラを編成し、HEX マスの盤面で戦うブラウザ向けのシミュレーション RPG。第1章（6ステージ）まで遊べる。アカウントを作れば、どの端末からでも同じデータで続きを遊べる。
- **自分の担当**：1人で開発した。企画、UI、データ設計と、画面・サーバーの設計を自分で決めた。コードの大部分は LLM に書かせ、すべて読んで理解したうえで取り込んでいる。
- **見どころ**：[どの端末でも同じ見た目にする](#どの端末でも同じ見た目にする)、[ゲーム内の値をサーバーで決める](#ゲーム内の値をサーバーで決める)、[LLM の案を採用しなかった判断](#ログインとパスワード)

| 項目 | 内容 |
| --- | --- |
| 開発体制 | 1人 |
| 開発期間 | 2026/06〜（開発中） |
| 動作環境 | ブラウザ（Chromium 系推奨） |
| 画面側 | TypeScript／React 19／zustand／Vite |
| サーバー側 | Cloudflare Workers／Cloudflare D1（SQLite） |

LLM との分担は[最後の節](#llm-との分担)にまとめた。

## 作った理由

これまでの自作ゲームは、友人に遊んでもらう段階で問題が出ていた。友人の PC では意図と違う大きさで表示され、セーブデータが消えることもあった。配布とデータの保存の方法は、作品ごとに変えてきた。

本作では「どの端末でも同じ見た目、同じデータで続きを遊べる」ことを目標にした。見た目は画面全体の拡大縮小で、データはサーバーで揃える。

## どの端末でも同じ見た目にする

これまでの作品では、メディアクエリで画面幅ごとにレイアウトを切り替えていた。この方法では境目ごとに別のレイアウトになるので、自分の環境で確かめた見た目と、友人の PC での見た目が一致しなかった。

アルバイト先では、入力内容のプレビューを画面に収まる大きさで表示する機能を作っていた。このとき使った「全体を拡大縮小して画面に収める」方法を、ゲームの表示に使うことにした。

画面は2つの層に分けている。

| 層 | 大きさ | 置くもの |
| --- | --- | --- |
| セーフエリア | 1920 × 1080 を比率を保って拡大縮小 | 盤面・メニューなど、見切れると困る中央に配置するもの |
| ビューポート | 端末の画面全体 | 背景、画面の端に寄せるボタン |

![スクリーン設計図](/images/posts/glacia/screen.avif)

拡大率は `min(画面の幅 / 1920, 画面の高さ / 1080)` で求めて CSS 変数 `--scale` に書き込み、ウィンドウの大きさが変わるたびに計算し直す。縦横の短いほうに合わせるので、セーフエリアはどの端末でも全体が画面に収まる。

16 : 9 でない画面では、セーフエリアの外に余白ができる。そこで背景はビューポート全体に敷き、端に寄せるボタンはセーフエリアではなく画面の端からの距離で置いた。これで画面の比率が変わっても余白が目立たない。

## ゲーム内の値をサーバーで決める

ガチャ、戦闘の報酬、キャラの強化など、ゲーム内の値が変わる操作はすべてサーバーで計算する。ブラウザ側の状態は開発者ツールで書き換えられるので、画面側で計算した値を保存すると、所持数などをいくらでも増やせてしまうからだ。画面側の状態（zustand）は表示にだけ使う。

サーバーには Cloudflare Workers を選んだ。無料枠が大きいこと、データベース（D1）を同じサービスの中で使えること、画面側と同じ TypeScript で書けることが理由である。同じ言語なら、スタミナなどのデータの定義を画面側とサーバー側で共有でき、変更のたびに両方を直さずに済む。

### 1回の操作の流れ

10連ガチャを例にすると、1回の操作は次のように処理する。

<Mermaid code={`
sequenceDiagram
  actor P as プレイヤー
  participant B as 画面<br>React＋zustand
  participant W as Cloudflare Workers
  participant D as D1
  P->>B: 10回引く
  B->>W: POST /gacha/pull { count: 10 }＋トークン
  W->>D: トークンからユーザーを特定
  W->>D: ユーザーデータを読む
  W->>W: 抽選・ジェムの消費を計算
  W->>D: 変わった行だけ書き込む
  W-->>B: ユーザーデータ全体＋抽選結果
  B->>B: 全ストアを置き換える
  B-->>P: 演出と結果を表示
`} />

どの操作も「読む → 計算する → 保存する → 返す」の順になる。そこで、この流れを Workers 側の1か所にまとめるよう自分から LLM に指示した。操作ごとに書くのは、操作前のユーザーデータとリクエストの中身を受け取り、操作後のユーザーデータを返す関数だけである。

```ts
// 操作ごとの関数の型
type Command<T> = (me: MeResponse, body: unknown, ctx: Context) => { me: MeResponse; result: T }

// すべての操作で共通の処理
const before = await loadMe(ctx)                         // D1 から読む
const after = command(before, await request.json(), ctx) // 計算する
await saveMe(ctx, before, after.me)                      // 変わった行だけ書く
return json({ me: after.me, result: after.result })
```

### 毎回ユーザーデータ全体を返す

どの操作でもユーザーデータ全体を返し、画面側はそれで全ストアを置き換える。これは自分から提案した設計で、理由は2つある。

1. 操作ごとに「何が変わったか」を返して画面に反映する処理を書かずに済む。
2. 画面とサーバーの値がずれても、次の操作で揃う。

その代わり、操作のたびにユーザーデータをすべて読むことになる。D1 の無料枠では、読み取りは1日500万行までである。アイテムやミッションの進行を別のテーブルに分けると、1回の操作で読む行数が増える。そこで正規化せず、`users` テーブルの1行に JSON の列として持たせ、ユーザーデータの読み取りが1行で済むようにした。

### 通信と書き込みを減らす

無料プランでは、1日の上限を超えると、リセットされる日本時間の朝9時まで D1 にクエリを送れなくなり、ゲームが遊べなくなる。そこで操作が多い箇所は通信をまとめた。編成やお知らせは画面を出るときに1回だけ保存し、戦闘中の盤面はサーバーに送らず結果だけを送る。サーバー側でも、操作の前後で変わった行だけを書き込む。

結果だけを送る作りには、クリアしていないステージをクリアしたと偽れる欠点がある。これは[残っている課題](#残っている課題)に書いた。

### 途中からサーバーへ移行した

サーバーは最初から Workers で作るつもりだったが、開発を始めた6月から約2か月半は手軽さを優先し、値を更新する処理を zustand のストアの関数として書いていた。ストアの関数は `set` でストアの状態を直接書き換えるので、そのままでは Workers に持っていけない。

一度にサーバーへ移すと、ストアからの切り出しとサーバーの構築を同時に進めることになる。そこで9月に、2段階に分けて移行した。

<Flow numbered>
  <FlowItem title="計算をストアから切り出す">
    値を変える処理を、ストアの中から `features/` の純粋関数に移した。関数は「操作前のデータ → 操作後のデータ」の形にし、まずはサーバーの代わりにモックから呼んだ
  </FlowItem>
  <FlowItem title="Workers に差し替える">
    Workers と D1 を用意し、同じ関数を Workers から呼ぶようにした。画面側の変更はモックを消すことがほとんどだった
  </FlowItem>
</Flow>

計算の関数は画面にもサーバーにも依存しないので、Workers 側は画面側のソースコードから直接 import している。最初はデータの定義だけを共有するつもりだったが、画面とサーバーを同じリポジトリに置いたことで、計算の関数や型も共有できた。

ただ、共有する関数が画面のコードを import すると、Workers からは使えなくなる。フォルダをきれいに分けたいとは前から思っていたが、方法が分からず、それまでは気をつけて書くだけだった。SNS で「依存の向き」という考え方を知り、ESLint の設定で import できる向きを決めた。

| フォルダ | import できないもの |
| --- | --- |
| `features/`・`data/`（ゲームのルールとデータ） | React、zustand、画面・状態・通信のコード |
| `worker/` | `src/` のうち `features/` と `data/` 以外 |

これで、ルールのコードが画面に依存すると ESLint のエラーになる。

サーバーへ移すことは最初から決めていたのだから、はじめから `features/` の関数として書いておけば、この切り出しの手間はかからなかった。

## ログインとパスワード

誰の操作かは、リクエストの中身ではなく、ログイン時に発行したトークンから決める。トークンは D1 にハッシュで保存し、ログインに失敗したときはユーザー名とパスワードのどちらが違ったかを返さない。

パスワードのハッシュ化には、LLM は最初 bcrypt を提案した。しかし bcrypt はわざと計算を重くした方式で、Workers の無料プランの CPU 時間の上限（1回のリクエストあたり 10ms）を超えてしまう。そこで bcrypt は使わないと決め、LLM が代わりに出した次の方式を採用した。

- ユーザーごとにランダムなソルトを作り、パスワードに付ける
- Workers の secret に置いた鍵（ペッパー）で HMAC-SHA256 を計算する

HMAC-SHA256 は計算が速いので、bcrypt に比べると総当たりに弱い。ただしペッパーは D1 ではなく Workers の secret にあるので、D1 の中身だけが漏れても、ペッパーが分からなければ総当たりを始められない。

## 戦闘の仕組み

### HEX 座標

HEX マスの座標の持ち方は1通りではない。[Red Blob Games の解説](https://www.redblobgames.com/grids/hexagons/)で主な座標系を比べ、斜交座標を選んだ。

| 座標系 | 持ち方 | 隣接マス | 距離・回転 |
| --- | --- | --- | --- |
| オフセット座標 | 行と列（2次元配列と同じ） | 偶数行と奇数行で差分が変わる | 一度ほかの座標系への変換が要る |
| キューブ座標 | (q, r, s)、ただし q + r + s = 0 | 6方向の差分を足すだけ | 式1つで求まる |
| 斜交座標 | キューブ座標から s を省いた (q, r) | 同上 | 同上（s = −q − r で戻せる） |

オフセット座標は見た目どおりで分かりやすいが、行の偶奇で計算が分かれ、移動範囲やスキル範囲の計算が複雑になる。キューブ座標は計算が単純だが、値を1つ余分に持つ。斜交座標はキューブ座標と同じ計算をそのまま使え、値は2つで済む。

### スキルの範囲をデータで書く

スキルは、狙えるマス（射程）と、そこに当たったときに効果が及ぶマス（効果範囲）をデータで定義する。範囲の判定は共通の処理で行うので、スキルを増やしても判定側のコードは変えない。

| 種類 | 定義 | 向き |
| --- | --- | --- |
| 距離型（`range`） | 自分からの距離が min 以上 max 以下のマス | なし |
| 形型（`pattern`） | 東向きを基準にした相対座標の集まり | 6方向のどれかに回して使う |

たとえば次のスキルは隣の1マスを狙い、狙ったマスと、術者から見たその左右の計3マスに当たる（定義の一部）。

```ts
{
  id: 'hoge',
  apCost: 4,
  range: { kind: 'range', max: 1 },  // 射程: 隣の1マス
  effect: [{
    type: 'damage', power: 160, target: 'enemy',
    // 効果範囲: 狙ったマスと、術者から見たその左右
    area: { kind: 'pattern', offsets: [{ q: 0, r: 0 }, { q: 0, r: -1 }, { q: -1, r: 1 }] },
  }],
}
```

最初は距離型のスキルしかなく、回転が要らないので、座標は斜交座標だけで扱えると考えていた。その後に形型を足すと、形を6方向に回す処理が必要になった。回転はキューブ座標のほうが式が単純なので、この処理の中だけ斜交座標からキューブ座標に戻して回している。

範囲をデータで書いていたので、不具合をデータの修正で直せたこともある。以前は「自分のマスは射程の形に関係なく常に狙える」という例外を判定処理に入れていた。`target` が `enemy` のスキルなら自分を選んでもダメージを受けず、`target` が `ally` のスキルは回復などなので自分も狙えたほうがよい、と考えたからだ。しかしこの例外のせいで、射程に自分のマスを含まないスキルでも自分のマスを狙えてしまった。効果範囲が複数マスに及ぶスキルでは、射程では狙えない隣の敵にまで当たっていた。例外を消し、自分を対象にするスキルは射程を `{ kind: 'range', min: 0, max: 0 }` と明示的に書くようにして直した。

## LLM との分担

| 部分 | 担当 |
| --- | --- |
| 企画・UI・データ設計 | 自分 |
| 画面とサーバーの設計 | 自分 |
| コード | 大部分を LLM。すべて読んで理解したうえで取り込んだ |

設計のうち、自分から LLM に提案・指示したものは次のとおりである。

- 操作の共通処理を1か所にまとめる（[1回の操作の流れ](#1回の操作の流れ)）
- 毎回ユーザーデータ全体を返し、ユーザーデータを JSON の列で持つ（[毎回ユーザーデータ全体を返す](#毎回ユーザーデータ全体を返す)）

- フォルダ間で import できる向きを ESLint で決める（[途中からサーバーへ移行した](#途中からサーバーへ移行した)）

## 残っている課題

戦闘の勝敗は、画面側から「勝った」「負けた」を送っている。戦闘は画面側で進めるので、サーバーは勝敗の申告をそのまま受け取るしかなく、実際には勝っていない戦闘の報酬を受け取るリクエストも送れてしまう。報酬の中身とドロップの抽選はサーバーで決めているが、勝敗そのものは検証していない。戦闘中の操作を1手ずつサーバーに送れば検証できるが、戦闘は戻るボタンで何度でもやり直せるので、書き込みが増えすぎる。

対策としては、戦闘中の操作の記録を結果と一緒に1回で送り、サーバーで同じ戦闘を再現して勝敗を確かめる方法が考えられる。戦闘の処理は `features/battle/` の関数にまとまっていて乱数も使っていないので、同じ操作の列を与えればサーバーでも同じ結果が得られる。

ただ、このゲームには他のプレイヤーと関わる要素がなく、不正をしても影響はそのプレイヤー自身のデータにしか及ばない。まだ開発中でほかに作るべき機能が多いので、この対策は優先度を下げて未実装にしている。
