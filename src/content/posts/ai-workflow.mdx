## 概要

2026/04 に Claude Pro を契約してから、個人開発では実装の大部分を Claude Code に書かせている。

進め方の基本は、作業を小さく分けて1つずつ任せ、そのたびに確かめることである。出力が意図とずれたら、AI に何が足りなかったのかを考え、それを足す。どこまで中身を理解しながら進めるかは、作品ごとに変えている。

## 作品ごとに関与の深さを変える

| 作品 | 進め方 | 理由 |
| --- | --- | --- |
| ゲーム（[氷途](../glacia/)など） | 設計は自分で決めて指示し（[例](../glacia/#llm-との分担)）、1歩ずつ書かせて中身をすべて理解しながら進める | 3年間続けてきた一番の関心で、仕組みを自分で説明できる状態にしておきたい |
| 音楽再生アプリ（[SymPony Music](../sympony-music/)） | まず動くものを作り、後から足したテストが通れば、そのコードを正しいとみなす | 自分が毎日使う道具で、正しく動くことが目的。Rust と Kotlin は書いた経験がなかった |
| このポートフォリオ、趣味のプログラム | 自分で書く | [最後の節](#自分で書く部分)に書いた |

同じ作品の中でも、作業ごとに出力を読む深さを変えている（[後述](#正解があるかどうかで読む深さを変える)）。

## 小さく分けて確かめる

### 作業を数分で終わる単位に分ける

実装を渡すときは、数分で終わる単位まで作業を分けて1つずつ渡している。一度に渡す範囲が小さいほど、指示とずれた出力にすぐ気づけ、確認する量も少なくて済む。大きな作業をまとめて渡すと、ずれが見つかったときに、どこから違っていたのかを探すのに時間がかかる。

### 正解があるかどうかで読む深さを変える

出力をどこまで読むかは、正解となるものが手元にあるかどうかで変えている。

| 作業の種類 | 例 | 確認の仕方 |
| --- | --- | --- |
| 正解となるものがない | 新しいロジックを書かせる | Lint と型チェックを通したうえで、中身をすべて読む |
| 正解となるものがある | ライブラリの差し替え、HTML のデモから React への移行 | 動作と見た目を確認して判断し、コードは理解のために目を通す |

新しいロジックでは、Lint と型チェックを通っても意図と違う実装が残るので、読んだうえで自分で直すことも多い。一方、正解となるものがあれば、AI が推測で補う部分がほとんどなく、前後で動作や見た目が変わらなければ正しいと判断できる。

### 使って確かめる

作ったものは自分で使って確かめる。氷途では、テストプレイ中に、選択肢のある行に戻ると選択肢が表示されない不具合に気づいた。原因は見てすぐ分かったので、原因を伝えたうえで、直す箇所を探して直す作業は AI に任せた。

一方、見た目では気づけない処理は、後から単体テストを足して確かめる。SymPony Music では、シャッフルやおすすめの順位など、結果が少し違っても画面では分からない処理にテストを書いている（[詳細](../sympony-music/#テスト)）。

## ずれたときに足すもの

出力が意図とずれたときは、直させる前に、AI に何が足りなかったのかを考える。足りなかったものによって、足すものが変わる。

| ずれの原因 | 例 | 足したもの |
| --- | --- | --- |
| 環境の前提が伝わっていない | パスワードのハッシュ化に bcrypt を提案された | Workers の CPU 時間の上限を伝え、方式を変えさせた |
| AI の知識が足りない | Android での再生が、何度書かせても動かない | 資料を自分で選び、それだけを参照させた |
| チーム内で前提がずれる | ハッカソンで、フロントとバックの API の形式が合わない | API の形式をまとめたドキュメントを両方のリポジトリに置いた |
| 決めた構造が崩れるおそれ | 画面とサーバーで共有するコードは、画面のコードに依存するとサーバーで使えなくなる | ESLint で import を制限し、編集のたびに確かめる |
| 自分の感覚でしか決められない | 曲調のタグの判定 | 学習に使うタグを自分で付けた |

**環境の前提**：今の LLM は一般的な知識を十分に持っているが、自分の環境の前提は、会話かリポジトリに書かれていなければ分からない。氷途で LLM が提案した bcrypt は一般には妥当な選択だが、わざと計算を重くした方式で、氷途が使っている Workers の無料プランの CPU 時間の上限（1回のリクエストあたり 10ms）を超える。bcrypt は使わないと伝え、代わりに出てきたソルトとペッパー付きの HMAC-SHA256 を、仕組みを理解したうえで採用した（[詳細](../glacia/#ログインとパスワード)）。

**AI の知識**：SymPony Music の Android での再生は、Claude Code に何度書かせても動かなかった。Android の公式ドキュメント、解説記事、それらのサンプルのリポジトリを自分で探し、使えると判断したものだけを参照させたところ、再生できるようになった。

**チーム内の前提**：楽天のハッカソンでは、フロントエンドとバックエンドがそれぞれ API の形式を変えてしまい、互いの形式が合わなくなった。現在の API の形式をまとめたドキュメントを両方のリポジトリに置き、AI に実装させるときもそれを読ませたので、人が書く部分と AI が書く部分の形式が揃った（[詳細](../../internships/rakuten/)）。

**決めた構造**：氷途では、ゲームのルールのコードを画面とサーバーで共有している。ルールのコードが画面のコードを import するとサーバーで使えなくなるので、ESLint でこの向きの import を禁止した。ファイルを編集するたびに Lint を実行する設定にしている（[後述](#毎回の指示に頼らないための設定)）ので、AI が制限を破るとその場でエラーが返り、AI 自身が直す。

**自分の感覚**：SymPony Music の曲調のタグの自動付与では、モデルの学習は Claude Code に任せたが、学習に使うタグは自分で曲に付けた（エネルギー60曲、明暗87曲）。どの曲が「激しい」かは聴く人の感覚で決まるからだ。

## 毎回の指示に頼らないための設定

同じ注意を毎回指示に書かなくて済むよう、Claude Code の設定を整えている。

| 設定 | 内容 | 目的 |
| --- | --- | --- |
| CLAUDE.md（全プロジェクト共通） | 公開されている指針を取り入れた。前提が曖昧なら質問する、頼まれていない機能を足さない、依頼と関係のない箇所を変えない、など | 頼んでいない変更を減らし、確認する量を抑える |
| CLAUDE.md（プロジェクトごと） | ディレクトリ構成、守るべき慣習、コマンド | 既存の書き方に合わせたコードを出させる |
| 権限の設定 | `.env` の読み書きを禁止する。強制プッシュと `git reset --hard` を禁止する。ファイルの削除やライブラリのインストールは毎回確認する | API キーなどの秘密情報を AI に渡さない。取り消せない操作を AI だけで行わせない |
| ファイル編集後のフック | TypeScript のファイルを編集するたびに Lint と `tsc --noEmit` を実行し、エラーを AI に返す | 型と Lint の誤りを AI 自身に直させ、自分は中身の確認に集中する |
| コミットメッセージのスキル | 書式を統一し、差分に危ない変更があれば指摘させる | 履歴から変更の種類を追えるようにする |

## 自分で書く部分

Astro で作っているサイトと、趣味のプログラムは自分で書いている。細かな修正も自分の手で書く。

Astro は気に入って使っているフレームワークで、このポートフォリオとメインのサイトは、Markdown を処理するプラグインも含めてほとんど自分で書き、リファクタリングを続けている。

趣味のプログラムは、ゲームの最適解を探すものが多い。今は、隣り合う国の名前を交互に言い合う[国境しりとり](https://coiluck.moe/CountryChain/)で、地図を見ながら遊ぶ人にも必ず勝つ CPU を作っている。

自分で考えて少しずつ組み立てる時間も好きなので、その時間は残している。自分で書いた経験は、AI の出力を読むときにも役に立っている。[シナリオエンジン](../novel-engine/)では、LLM で書き直した版と自分で2年間書いてきた版を比べて、自分の設計のどこが外れていたかが分かった。比べられたのは、自分で書いた版があったからだ。
