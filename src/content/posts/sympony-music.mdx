## 作品概要

- **何を作ったか**：端末に保存した曲を再生する Windows・Android 向けのアプリ。タグの条件で曲を集めるプレイリスト、曲ごとの音量の自動調整、曲調のタグの自動付与を備え、大学3年からの電車通学で毎日使っている。
- **自分の担当**：仕様の決定、React の画面、デスクトップ版の再生処理。未経験だった Rust と Kotlin の部分は Claude Code に書かせ、参照させる資料の選定と実機での確認を自分で行った。
- **見どころ**：[Android で曲を鳴らすまで](#android-で曲を鳴らすまで)、[曲調のタグの自動付与](#曲調のタグを自動で付ける)、[テスト](#テスト)

| 項目 | 内容 |
| --- | --- |
| 開発体制 | 1人 |
| 動作環境 | Windows／Android |
| 画面 | TypeScript／React 19／zustand／Vite |
| アプリ本体 | Tauri 2／Rust／SQLite |
| Android の再生 | Kotlin／Media3（ExoPlayer） |

AI との分担の詳細は[最後の節](#ai-に任せた範囲)にまとめた。

## 作った理由

大学3年から通学で電車に乗る時間が長くなり、スマートフォンで聴けるアプリが必要になった。それまで使っていたアプリは広告が煩わしく、曲ごとに音の大きさが違う点も気になっていた。以前自作した再生アプリは Electron で作ったので、パソコンでしか動かなかった。

Windows と Android の両方で動かすために、Tauri 2 を選んだ。理由は次の3つである。

1. 画面を TypeScript と React で書ける。以前作った再生アプリやゲームのコードから、再生処理などを移植しやすいと考えた。ただし実際には、そのまま使える部分は少なかった。
2. 同じく Web の技術で画面を書ける Wails は、当時モバイルに対応していなかった。ライブラリや情報の量も Tauri のほうが多い。
3. React Native では画面を DOM と CSS で書けないので学習が必要で、自分がフロントを担当するときに実装速度が遅くなるのではという心配があった。

## Android で曲を鳴らすまで

開発で最も時間がかかったのは Android での再生だった。WebView の `<audio>` で曲を再生すると30秒前後で止まった。自分は Kotlin を読めず、Android の再生の仕組みにも詳しくなかったので、Claude Code に書かせても動かない状態が続いた。

そこで、Android のネイティブ側で曲を再生する方法を自分で調べた。公式ドキュメント、解説記事、それらのサンプルのリポジトリを探し、使えると判断したものだけを Claude Code に参照させて書かせた。

5/9 に、Android の再生を Kotlin の再生サービスに移した。サービスは Media3（Android 公式の再生ライブラリ）の上に作ったので、ロック画面や通知からの操作、Bluetooth 機器のボタン、他のアプリとの音声の切り替えを Media3 が扱う。動作は実機で確かめている。

## 音量と曲末尾の無音

曲を読み込むときに、Rust で各曲の音量（ラウドネス、LUFS という単位で表す）と末尾の無音の長さを解析して DB に保存する。

| 機能 | 内容 |
| --- | --- |
| 音量の調整 | 目標の -14 LUFS との差から、曲ごとに音量の倍率を決める（6 LUFS 大きい曲なら約0.5倍） |
| 末尾の無音 | 無音が始まる位置まで来たら、曲の終わりを待たずに次の曲へ進む |

解析には1曲ごとに時間がかかるので、読み込みの処理を2段に分けた。先に曲の情報だけを DB に登録して一覧に出し、重い解析はその後に行う。これは Windows 向けに以前作ったときに自分が決めた。これにより、曲を追加したときに解析が終わるまで一覧が空のまま待たされることがない。

## タグで曲を集める

プレイリストには、曲を手で追加する通常のものに加えて、タグの条件で曲を集めるもの（タグリスト）がある。タグリストには「含むタグ」と「除くタグ」を設定し、含むタグをすべて持ち、除くタグを1つも持たない曲を集める。曲にタグを付ければ、該当するタグリストに自動で入る。

これは実装を決めたときから自分が入れたかった機能だった。通常のプレイリストでは曲の追加や削除が面倒で、中身が次第に固定されてしまっていたからだ。

```ts
export function matchesTags(
  tags: readonly string[], // 1 曲についているタグの配列
  include: readonly string[],
  exclude: readonly string[] = [],
): boolean {
  const tagSet = new Set(tags)
  return include.every(tag => tagSet.has(tag)) && !exclude.some(tag => tagSet.has(tag))
}
```

### 曲調のタグを自動で付ける

タグリストは「自分で新規に追加した曲を再生リストに反映させる処理が面倒」という理由で実装した。しかし使っている中で、結局曲自体に自分でタグをつける必要があり、手間が軽減されていないことに気がついた。そこで 10月の版（1.4.0）で、曲調のタグを自動で付けるようにした。

| 軸 | タグ |
| --- | --- |
| エネルギー | 静／動／激 |
| 明暗 | 明／暗 |

推定には [Essentia](https://essentia.upf.edu/models.html) の学習済みモデル（楽器、ムード、ダンスのしやすさなどを出力する）を使っていて、学習は Claude Code にやらせている。 Essentia の出力をそのままタグにするのではなく、自分の手元の曲に自分でタグを付けたデータから線形モデルを学習し、Essentia の出力と音の特徴量を「静／動／激」「明／暗」に変換する重みを作ってもらった。どの曲が「激」に当たるかは聴く人の感覚で決まるので、自分の感覚に合わせたかったからだ。

Essentia のモデルは Rust から読み込んで動かし、推定はスマートフォンの CPU だけで行う。

軸の分け方は、最初からこの形だったわけではない。はじめはエネルギーを「激／動／凛／静」の4段階で分けるつもりだった。しかし、自分の中では明確に違う「動」（躍動感がある）と「凛」（疾走感があって爽やか）が、モデルの出力の上ではうまく分かれなかった。そこで、エネルギーの3段階と明暗の2段階という2つの軸に分け直した。

手元のラベル（エネルギー60曲、明暗87曲）で1曲ずつ抜いて検証すると、正解率はエネルギーが0.57、明暗が0.90だった。エネルギーは3段階から選ぶので正解率は低めだが、外れた曲はすべて隣の段階に判定されており、「静」の曲を「激」と判定するような外れ方はなかった。

## テスト

画面の操作で起きる問題は、毎日使っていればすぐに気づける。一方、おすすめの順位やシャッフルのように、結果が少し違っても見た目では分からない処理は、間違っていても気づかないまま使い続けるおそれがある。そうした処理に単体テストを書き、画面側は Vitest、Rust 側は cargo test で実行している。

| 対象 | 確かめていること |
| --- | --- |
| おすすめの順位 | 履歴に多いタグやアーティストの曲が上位に来る、直近に聴いた曲は下位になる、全曲で同じ値の要素は順位に影響しない |
| シャッフル | 元の配列を書き換えない、曲が増えたり減ったりしない、先頭の曲も入れ替わる |
| Android の曲の切り替え | 先に進むと飛ばした曲を履歴に積んでキューから外し、前に戻ると戻った分をキューの先頭に返す |
| 聴いた時間の記録 | 5秒進むごとに1回だけ DB に書く、記録の開始が DB に書き込まれる前に曲が終わっても、その曲の記録に書く |
| 曲調のタグの付与（Rust） | 自分で付けたタグがある軸には追加しない、エネルギーと明暗を別々に判定する |
| 曲調のスコア（Rust） | 決まった入力に対して、前と同じスコアを返す |

シャッフルのテストで先頭の曲が入れ替わることまで確かめているのは、シャッフルの実装（Fisher–Yates 法）で添字の範囲を1つ間違えると、先頭の曲が絶対に動かなくなるからである。この間違いは、曲が並び替わったことを目で見るだけでは気づきにくい。曲調のスコアのテストは、特徴量の計算を書き換えたときに、意図せず推定結果まで変わったことに気づくためのものである。

音量の調整と末尾の無音の読み飛ばしは、音の大きい曲、小さい曲、末尾の無音が長い曲を集めたプレイリストを作り、実機で再生して確かめた。

## 残っている課題

ピアノだけの曲では、曲調のタグが自分の感覚と合わないことがある。友人に使ってもらう中で見つかった問題で、学習に使う曲とタグを見直して対応を進めている。
