## 作品概要

- **何を作ったか**：ノベルゲームの進行を管理するエンジン。クリックでテキストを進め、背景・立ち絵の切り替え、選択肢による分岐、戻る、セーブ・ロードを扱う。2024/11 から、自作ゲームを作るたびに機能を足してきた。
- **自分の担当**：2026/03 の版までは、設計も実装も自分で行った。この版は DLsite で販売している作品（[ツクヨミスイッチ](https://www.dlsite.com/ai/work/=/product_id/RJ01575101.html)）に使っている。現在の版は、氷途で画面を React に置き換えるときに LLM に書き直させたものである。
- **見どころ**：[戻るボタンを付けて破綻した経緯](#背景と立ち絵が戻らない)、[LLM で書き直した版と比べて分かったこと](#llm-で書き直した版と比べて分かったこと)

このページでは、自分で書いた最後の版（2026/03）を中心に、何を考えてどう作り、どこで破綻したかを書く。最後に LLM で書き直した現在の版と比べ、当時の自分の判断のどこが外れていたかを書く。

## 自分で書いた最後の版

2026/03 の版は、DLsite で販売している作品に使った。リポジトリは公開していないので、コードは抜粋して載せる。

2025/09 の版から、次の機能を足した。シナリオを進める処理のファイルは、142行から453行になった。

| | 2025/09 の版 | 2026/03 の版 |
| --- | --- | --- |
| 分岐 | 変数1つで持つ。分岐の中で分岐できない | スタックで持ち、何段でも入れ子にできる |
| 戻る | なし | 表示した地点を履歴に積み、ボタンとマウスホイールで戻れる |
| セーブ・ロード | なし | 位置と背景・立ち絵・BGM を保存し、途中から再開できる |
| 演出 | `action` を呼ぶだけ | `action` の完了を待ってから次の行へ進む |
| テキスト | 一度に表示 | 1文字ずつ表示し、速度を設定できる |
| エンディング | なし | 通った選択肢から判定し、ギャラリーに記録する |

以下では、このうち分岐、戻る、セーブ・ロードについて書く。

### 分岐の中の分岐

2025/09 の版では、分岐を変数1つで持っていたので、分岐の中でさらに分岐できなかった。2026/03 の版では、分岐の状態をスタック（後から積んだものを先に取り出す配列）で持った。分岐に入るときに「どの分岐の何行目にいるか」を積み、分岐を読み終えたら取り出して、親の分岐の続きに戻る。以下ではこれを分岐スタックと呼ぶ。

### 戻るボタン

同じ版で、テキスト欄の近くに戻るボタンを付けた。Key やゆずソフトの作品には戻るボタンがあり、ノベルゲームにはあるのが普通だと思っていたので、深く検討せずに付けることにした。

分岐スタックは「今どこにいるか」しか持っていない。上の図で B → W を選び、W を読み終えて b-3 に戻ってきたとき、分岐スタックには B の b-3 しかなく、直前に W を通ったことは分からない。そこで、表示した地点を履歴として積むことにした。履歴には、位置と分岐スタックの写しだけを入れた。

```js
// 表示した地点を履歴に追加（抜粋）
displayHistory.push({
  branchStackData: branchStack.map(b => ({ choiceId: b.choiceId, choiceIndex: b.choiceIndex, index: b.index })),
  index: index,
  openingStoryIndex: openingStoryIndex,
});
```

戻るときは、1つ前の履歴から位置と分岐スタックを復元し、その行のテキストを表示し直す。

```js
// 戻るボタン（抜粋）
displayHistory.pop(); // 今の地点を捨てる
const prevState = displayHistory[displayHistory.length - 1];
branchStack = restoreBranchStack(prevState.branchStackData);
openingStoryIndex = prevState.openingStoryIndex; // 本筋の何行目か
displayStory(prevState.index, false); // false: action を実行しない
```

### 背景と立ち絵が戻らない

テストプレイ中に、戻ってもテキストしか戻らないことに気づいた。b-3 で背景を変えていた場合、w-2 に戻るとテキストは w-2 になるが、背景は b-3 のままになる。立ち絵も同じだった。

原因は、背景や立ち絵の変更を `action` という関数で書いていたことにある。関数は実行すると画面を書き換えるだけで、その結果はどこにも残らない。履歴には位置しか入っていないので、その地点の背景が何だったかが分からない。戻った先の行の `action` を実行し直しても、それより前の行で変えた背景は戻らない。

### セーブは別の方法で復元していた

セーブ・ロードでは、位置とは別に、最後に表示した背景・立ち絵1人分・BGM を個別に保存して復元していた。

```js
// ロード時の復元（抜粋、一部簡略化）
backgroundImage.src = globalGameState.LoadImageSrc;
bgm.play(globalGameState.LastBGM);
// 立ち絵は「顔を表示するか/キャラ/ポーズ」を / でつないだ文字列で持っていた
const [hasFace, id, pose] = globalGameState.LastCharacter.split('/');
```

ロードでは背景と立ち絵を戻せるのに、戻るボタンでは戻せない。画面の状態を1か所にまとめて持っていなかったので、機能ごとに別々の方法で復元していた。

### 選択肢より前に戻れない

選択肢を選ぶと履歴を消し、選択肢より前に戻ろうとすると「選択肢より前には戻れません」と表示していた。

戻った先では、`action` だけでなく選択肢も表示しない作りになっていた。履歴を消していなければ、選択肢の行まで戻ったときに選択肢が出ず、次のクリックで分岐を飛ばして本筋に進んでしまう。ただ、ゲームの内容と関係のない文は、プレイヤーに見せたくなかった。

### 当時考えた直し方と、見送った理由

各地点の状態をすべて記録しておき、戻るときに丸ごと復元すれば直ることは、当時も考えた。しかし、行を進めるたびに状態を丸ごと積むと、履歴がどこまでも大きくなるのが嫌だった。位置などの少ない情報だけから復元する方法があるはずだと考え、丸ごと記録する方法は筋が悪いと判断した。

どちらの方法でも、エンジンの中心部分と、シナリオを書く Markdown、それをシナリオのデータに変換するスクリプトまで直すことになる。修正はこの作品では見送った。作りたいものはまだいくらでもあり、1つの作品の修正に時間をかけるより先に進みたかった。友人に遊んでもらって感想をもらうのが制作の励みになっているので、早く遊んでもらいたかったのもある。

## LLM で書き直した版と比べて分かったこと

次の作品（氷途）では、画面を React に置き換えた。それまでのエンジンは内部で DOM を直接操作していて、作品を作るたびに DOM の構造まで移植する必要があり、これが不満だったからだ。置き換えは LLM に書かせ、あわせてエンジンも書き直した。状態を丸ごと記録する作りについて、履歴が膨らむのが嫌だと自分が伝えたところ、LLM が履歴に上限を設ける方法を提案したので、それを採用した。

| | 2026/03 の版（自分） | 現在の版（LLM） |
| --- | --- | --- |
| 演出 | 関数（`action`）を実行する | データの命令。状態を変える命令と、その場の演出に分ける |
| 履歴に残すもの | 位置と分岐スタック | ゲームの状態すべて（最大50件） |
| 戻る | 位置を戻し、テキストだけ表示し直す | 履歴の状態で置き換える |
| セーブ・ロード | 最後の背景・立ち絵・BGM を個別に保存 | 履歴と同じ状態を保存する |
| 選択肢より前に戻る | できない | できる |

現在の版では、シナリオの1行を次のように書く。背景を変える `bg` は状態を変える命令で、背景を動かす `bgMove` はその場の演出である。状態を変える命令だけを純粋関数で適用し、結果をデータとして履歴に積む。

```ts
{
  text: '港に着いた。',
  speaker: 'キャラA',
  commands: [
    { type: 'bg', file: 'ice_port.avif', transition: 'crossfade' }, // 状態を変える命令
    { type: 'bgMove', direction: 'leftToRight', duration: 5000 },   // その場の演出
  ],
}
```

読み比べて、当時の判断について2つのことが分かった。

**履歴が大きくなる心配は小さかった。** 演出をデータで書けば、1地点の状態は、背景のファイル名、立ち絵の一覧、テキスト、位置、好感度などの値だけになる。JSON にすると1件 0.5KB ほどで、上限の50件を積んでも 25KB ほどにしかならない（大まかな見積もり）。

**本当の問題は、演出を関数で書いていたことだった。** 位置だけから復元する自分の案も、演出がデータなら成り立つ。選んだ選択肢と位置が分かれば、最初の行から命令を順に適用し直して、その地点の状態を作れるからだ。2026/03 の版でこれができなかったのは、`action` が画面を書き換えるだけの関数で、状態を計算できなかったからである。関数のままでは、丸ごと記録しようとしても画面そのものを写し取るしかない。丸ごと記録する案を重く感じたのも、位置から復元する案が通らなかったのも、原因は同じだった。
